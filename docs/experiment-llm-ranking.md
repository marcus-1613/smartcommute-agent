# 对照实验：路线排序该由谁承担？

> 实验脚本：[scripts/experiment_llm_ranking.py](../scripts/experiment_llm_ranking.py)
> 关联决策：[design-decisions.md 决策 1](design-decisions.md)

## 为什么要做这个实验

项目里有一条设计决策：「LLM 只负责需求解析与解释生成，路线排序交给确定性代码」。

做这个决定时，我给出的理由里有一条是「让 LLM 排序，同样的输入两次可能给出不同排序」。
**这条理由从未被验证过，它只是一个听起来合理的假设。** 而这个假设是整个决策的地基——
如果它不成立，决策就需要换一个理由，或者根本不成立。

所以做了这个实验：**用项目真实的评分器和真实的模型调用路径，测一测到底会怎样。**

## 实验设计

**输入**：4 条刻意构造出真实取舍的候选路线（没有任何一条全面占优）。

| 路线 | 耗时 | 票价 | 步行 | 换乘 |
|---|---|---|---|---|
| A | 31.4 min | S$2.07 | 38.5 m | 1 |
| B | 45.2 min | S$1.20 | 120.0 m | 0 |
| C | 26.1 min | S$2.80 | 250.0 m | 2 |
| D | 38.0 min | S$1.75 | 80.0 m | 1 |

**场景**：同一句需求，四种偏好侧重（少换乘 / 少走路 / 省钱 / 求快）。

**对比双方**：

- **确定性评分器**：项目里实际使用的 `score_routes()`，加权多指标 + 硬约束。
- **大模型**：复用生产代码的调用路径 `DeepSeekLLMService._chat_json`
  （**`temperature=0` + JSON 模式**，与线上完全一致）。

这一步很关键：如果换一种调用方式去测，测出来的结论不能代表线上行为。

**指标**：

- **稳定性**：同一输入重复 10 次，排序结果是否变化。
- **一致性**：大模型给出的排序，与确定性评分器的排序是否相同。

## 实验结果

每个场景重复 10 次，共 40 次调用（2026-10 实测）：

| 场景 | 确定性首推 | 大模型首推 | 大模型排序变化 | 与确定性一致率 |
|---|---|---|---|---|
| 少换乘优先 | A | B | 0 / 10 | 0% |
| 少走路优先 | A | B | 0 / 10 | 0% |
| 省钱优先 | A | B | 0 / 10 | 0% |
| 求快优先 | A | C | 0 / 10 | 0% |

**汇总**：

- 确定性排序变化：**0 / 40**（纯函数，恒为 0）
- 大模型排序变化：**0 / 40**
- 两者总体一致率：**0 / 40**

## 结论（包括推翻我原本假设的部分）

### 1. 原假设被推翻：「不可复现」不成立

`temperature=0` 下，大模型 40 次重复输出**完全一致**。

我原本以为它会不稳定，**这个判断是错的**。所以「同样的输入两次可能给出不同排序」
这条理由必须从决策依据里删掉——它经不起验证。

> 这件事本身值得记录：一个听起来合理的假设，如果不实测，
> 就会以「设计依据」的名义被写进文档，并且在面试被人追问时当场失效。

### 2. 真正的问题：排序依据**不可规定**，因而不可能调参

这不是「准不准」的问题，而是「你能不能指定它的取舍规则」的问题。

确定性评分器的依据是**显式**的：耗时权重 0.30、费用 0.20、步行 0.15、换乘 0.15……
权重可调、过程可复现、结果可写断言。想让它更看重换乘，改一个数就行。

大模型没有这个接口。你只能改提示词，然后**重新观察它变成什么样**——
没有参数可以调，没有过程可以解释，也无法写一个有意义的断言
（断言只能锁死「它这次恰好输出了什么」，输入一变就失效）。

实测中它的行为也印证了这一点：4 个场景里，3 个场景它选了字面最优的路线
（0 换乘、最便宜、最快），但在**「少走路」场景它选了步行 120 米的路线**，
而真正步行最少的是 A（38.5 米）。

**它大部分时候看起来合理，但你无法预测它下一次会怎么做，也无法纠正它。**

### 3. 决策维持，但理由要换

排序仍然交给确定性代码，但理由从「可复现」改为：

> **依据显式、可调参、可解释、可单测。**

### 4. 副产品：实验发现了确定性评分器的一个真实短板

这是做这个实验最大的意外收获。

`UserPreferences.effective_weights()` 对权重的调制幅度是固定的 **±40%**：

```python
w.duration *= 1.0 + self.prefer_shorter_time * 0.4
```

也就是说，`prefer_shorter_time = 0.5`（默认）和 `= 1.0`（最看重）之间，
耗时权重只差 20%。这**不足以表达用户口中的「特别」「尽量」**。

表现就是：「求快优先」场景下评分器首推 A（31.4 分钟），
而最快的 C 是 26.1 分钟。用户说了「越快越好」，评分器却没选最快的那条。

大模型在这个场景选的是 C——**它抓对了，评分器没抓对。**

这不是一个可以忽略的细节：**它说明加权模型在极端偏好下的表达力不足。**
记为改进项，后续可考虑：

- 让偏好直接映射到更强的权重区间（如 `1.0 + pref * 2.0`）
- 或对「硬偏好」与「软偏好」分级——用户说「特别怕换乘」时，
  更适合当成软约束而不是权重微调

## 复现方式

```bash
# 需要 .env 中配置 DEEPSEEK_API_KEY
python scripts/experiment_llm_ranking.py             # 每场景 10 次
python scripts/experiment_llm_ranking.py --runs 5
python scripts/experiment_llm_ranking.py --scenarios 2
```

## 实验本身的局限

- **样本量小**：4 条候选路线、4 个场景。结论用于**对比两种实现方式的性质差异**，
  不适合推断「大模型排序的准确率是多少」。
- **两边输入不完全对等**：确定性评分器接收的是数值化偏好（0.9），
  大模型接收的是用户原话。这使得对比更接近真实产品形态，
  但也意味着差异中既包含「排序依据」的差异，也包含「偏好表达能力」的差异——
  后者恰好被第 4 条结论捕捉到了。
- **单一模型**：只测了 `deepseek-chat`，其他模型未验证。
