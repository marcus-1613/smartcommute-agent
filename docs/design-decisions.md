# 关键技术决策记录

[architecture.md](architecture.md) 描述的是**系统当前如何工作**。
本文记录的是**为什么这样设计**——每条决策都包含当时考虑过的其他选项和付出的代价。

选择记录"代价"而不是只记录"优点"，是因为一个说不清代价的方案，通常意味着要么没想清楚，
要么在隐藏问题。

---

## 决策 1：LLM 只负责理解与表达，排序交给确定性代码

**背景**：路线推荐需要按用户偏好对多条候选路线排序。

**选项**

- A. 把候选路线交给 LLM，让它直接给出排序和理由；
- B. LLM 只做需求解析与推荐解释，排序由确定性 Python 代码完成。

**决定**：B。

**理由**：通勤推荐必须可复现、可解释、可测试。
方案 A 有三个无法回避的问题：相同输入两次可能给出不同排序（不可复现）；
给出排序后无法归因（不可解释）；断言"排序正确"几乎无法写进单测（不可测试）。
方案 B 把评分变成纯函数——权重归一化、缺失指标按中性值 0.5 处理、硬约束优先并标记不可行，
输出逐项明细，前端可直接展示"为什么推荐这条"。

**代价**：评分模型的表达能力受限于手写规则。
用户提出规则未覆盖的偏好（例如"尽量少晒太阳"）时，需要改代码而不是改提示词。

## 决策 2：会话状态与业务数据分离存储

**背景**：既要支持多轮会话恢复，又要持久化用户、消息、通勤计划等业务实体。

**选项**

- A. 全部塞进 LangGraph Checkpointer；
- B. Checkpointer 只存工作流状态，业务数据走 SQLAlchemy；
- C. 不用 Checkpointer，自己把工作流状态序列化进业务表。

**决定**：B。

**理由**：两者生命周期和访问模式不同。Checkpointer 存的是工作流的内部快照，
结构由 LangGraph 决定，升级框架时可能变化；业务数据是要被查询、分页、聚合的领域模型，
结构必须稳定。混在一起会让框架的存储格式绑死业务查询能力；
而方案 C 等于自己重新实现一遍状态持久化，还要处理并发与一致性。

**代价**：同一份会话信息存在两个存储里，排查问题时要同时看两边。

## 决策 3：数据源用适配器模式封装，并组成优先级降级链

**背景**：路线、交通事件、天气各有多个可选来源，且可用性依赖用户是否配置了密钥。

**决定**：为每类数据定义抽象接口，各来源实现为独立适配器；启动时按优先级选择。

| 维度 | 优先级 |
| --- | --- |
| 路线 | OneMap → Google Maps → Mock |
| 交通事件 | LTA DataMall → Mock |
| 天气 | Open-Meteo → Mock |

**理由**：最直接的收益是**没有密钥也能完整跑通**——Mock 不是临时占位，
而是降级链的最后一环，且会在界面上明确标注来源。
其次是新增来源（或替换路线引擎）只需新增一个适配器并在启动逻辑里注册，不必改工作流。

**代价**：多了一层抽象。调试真实来源的问题时，需要先确认实际选中了哪个适配器。

## 决策 4：拆成两个 MCP Server，而不是一个

**背景**：MCP 工具需要暴露 5 个能力：地点检索、路线查询、交通事件、天气查询、天气风险。

**选项**

- A. 单个 Server 暴露全部工具；
- B. 按数据域拆成 Mobility 与 Weather 两个 Server。

**决定**：B。

**理由**：拆分的边界与数据源边界对齐——Mobility 依赖 OneMap / Google / LTA，
Weather 依赖 Open-Meteo。两者密钥、限流、失败模式都不同，
隔离后一个域崩溃不会影响另一个域的进程。这也让"天气失败不影响路线推荐主体"
成为一个结构性保证，而不是靠异常处理凑出来的效果。

**代价**：每个工具调用都要新建一次 stdio 连接，比常驻进程开销大；
同时也引入了与 Windows 事件循环的兼容问题（详见 [lessons.md](lessons.md) 第 1 条）。

## 决策 5：不实现失败重试，改为错误隔离

**背景**：外部 API 可能超时、限流或返回异常结构。

**决定**：各节点独立捕获异常，失败的维度记入 `errors` 并如实标记为不可用，
不向上抛出；不使用统一的重试机制。

**理由**：这里的故障大多不是"抖一下就好"的类型——密钥缺失、配额耗尽、限流
这类问题重试只会浪费请求配额并延长用户等待。相比之下，**让单点失败不扩散**更重要：
天气查询失败不应该阻断路线推荐，交通事件失败不应该让整个请求报错。

**代价**：瞬时网络抖动会让该维度**直接变为不可用**，当次推荐因此缺少该维度的信息，
需要用户重新发起请求才会恢复。

注意这与"降级到 Mock"是两回事：只有**未配置密钥**时才会用 Mock 顶替，
**真实调用失败一律如实报错**，不会拿模拟数据冒充。因此该维度的界面标签会显示"不可用"而非"模拟"。

如果后续接入对稳定性要求更高的来源（例如实时到站），应为这类调用单独引入带退避的重试。

> 现状说明：`config.agent_max_retries` 与 `state.retry_count` 是早期设计的遗留字段，
> 目前未被任何逻辑使用。要么在引入重试时启用，要么删除，避免留下误导。

## 决策 6：默认 SQLite，仅预留 PostgreSQL

**决定**：本地开发与演示使用 SQLite，通过 `DATABASE_URL` 可切换到 PostgreSQL。

**理由**：这个项目的瓶颈在外部 API，不在数据库。
SQLite 零配置、单文件、随项目走，让"clone 下来就能跑"成立。
用 SQLAlchemy 的方言无关写法预留切换能力，避免过早引入数据库运维成本。

**代价**：SQLite 的并发写入能力有限，不适合多实例部署。
此外目前**没有引入 Alembic**，无法管理表结构演进——这是切换到 PostgreSQL 之前必须先补的部分。

## 决策 7：不引入 OpenTripPlanner

**决定**：路线引擎不替换为 OpenTripPlanner（OTP）。

**理由**：OTP 能解决的只有"多模式路线规划"这一个维度，
交通事件和天气仍然需要额外的数据源，**引入它并不会减少系统的组件数量**；
却要额外背上 Java 运行时、数 GB 的图构建（GTFS + OSM）以及持续更新的数据管道。
对当前阶段（演示 + 轻量部署）而言，这个代价换不回成比例的收益。

**代价**：路线数据依赖第三方 API（OneMap / Google），
无法本地化定制路由算法，也受对方的配额与可用性约束。

完整评估（含许可、数据构建、接入方式）见 [opentripplanner-evaluation.md](opentripplanner-evaluation.md)。
