# 问题记录与复盘

这里记录开发过程中真正卡住过的问题。每条按「现象 → 定位过程 → 根因 → 修复 → 沉淀」组织，
并且刻意保留**最初判断错的部分**——判断失误的过程比结论更有参考价值。

---

## 1. Windows 下 MCP 工具调用全部失败：事件循环不支持子进程

**现象**：后端接口调用 MCP 工具时全部报错，但把 MCP Server 单独启动、手动传入参数却完全正常。

**定位过程**

第一步怀疑 MCP SDK 版本或脚本路径有问题，逐一排除后确认两者都正常。
真正有用的信息来自异常栈——它最终落在一个看起来毫不相关的调用上：

```
asyncio.create_subprocess_exec(...)
```

顺着这条线索查下去，才把两件独立的事实连起来：

1. MCP 的 stdio 客户端必须 `spawn` 一个子进程来承载 Server；
2. Windows 上 uvicorn 会强制使用 `SelectorEventLoop`，而这个事件循环**不支持子进程**。

**根因**：业务代码运行的事件循环缺少 fork/exec 能力，与 MCP 的 stdio 传输方式在 Windows 上天然冲突。

**修复**：在专用后台线程中启动一个 `ProactorEventLoop`（Windows 上支持子进程），
所有 MCP 调用通过 `asyncio.run_coroutine_threadsafe` 提交到该循环执行，再用 `asyncio.wrap_future` 把结果桥回原循环。
非 Windows 平台直接在当前循环执行，不走这条路径。

**沉淀**：跨平台异步能力的差异应当隔离在集成边界处。这个适配只存在于 `mcp_client.py`，
Agent 工作流和 MCP Server 本身都不需要知道它存在。

## 2. 子进程收到中文参数变乱码

**现象**：中文地名传入 MCP Server 后变成乱码，地点解析直接查不到结果。

**根因**：Windows 子进程默认按系统代码页（简中环境下为 GBK）解码标准输入输出，而非 UTF-8。

**修复**：启动子进程时显式注入 `PYTHONUTF8=1` 与 `PYTHONIOENCODING=utf-8`。
同时把命令从裸 `"python"` 改为 `sys.executable`，避免 PATH 解析到与当前虚拟环境不同的解释器。

**沉淀**：只要跨进程边界传递文本，编码就必须显式声明，不能依赖平台默认值。

## 3. Checkpointer 退出异常：一度误判为 "aiosqlite 线程兼容问题"

**现象**：服务关闭时进程异常终止（SIGTERM），偶发会话状态未能落盘。

**定位过程（这条的价值在于走错的那一步）**

最初判断是 aiosqlite 与 asyncio 的线程模型不兼容——这个结论听起来合理，
而且网上确实能找到大量"aiosqlite 在 Windows 下不稳定"的讨论，于是差点直接换掉整个存储方案。

停下来重新看证据后发现，这个推断解释不了两件事：为什么大多数情况下是正常的？
为什么异常只发生在**进程退出时**？

顺着"只在退出时出错"重新排查，找到了两个真正的原因：

1. aiosqlite 连接**从未被关闭**，进程退出时的资源清理因此失败；
2. 调用 LangGraph 时的 `config` 缺少 `checkpoint_ns` 字段。

**修复**：引入 `CheckpointerManager` 统一管理创建与关闭，在 FastAPI lifespan 的 shutdown 阶段显式 `close()` 底层连接；补全 `checkpoint_ns`。

**沉淀**：**"看起来像已知问题"最容易让人停止推理。**
如果当时按"aiosqlite 不兼容"去换存储方案，不仅绕远路，还会把真实根因永久埋掉。
判断一个根因是否成立，要问它能否解释现象中的**全部**特征（比如何时发生、何时不发生）。

## 4. 意图分流：用规则短路会吞掉"话题跳转"

**现象**：多轮会话中用户突然问"什么是 LangGraph"，系统却继续推路线，或返回空白。

**最初做法**：把"是否已有通勤上下文"当成规则开关——有上下文就一律按上下文补充处理。

**问题**：这等于假设"多轮会话中用户只会聊同一件事"。
该假设不成立，于是话题跳转被吞掉；反过来，若一刀切按新意图处理，
又会把"换一条少走路的路线"这类真正的上下文补充误判成新需求。

**修复**：取消规则短路。解析需求之后**始终**执行一次意图分类，
把「已有通勤上下文」作为**特征**传给模型参与联合判断，
而不是作为**规则**直接决定分支。仅当分类器自身异常、且已有完整上下文时，才兜底按通勤处理，
避免多轮补充被丢弃。

**沉淀**：规则适合处理确定性判断，语义歧义应交给模型。
更普遍地：把上下文当作**特征**而不是**开关**，是处理多轮对话的通用原则。

## 5. 数据来源语义：把"请求成功"当成了"真实数据"

**现象**：早期实现只要 HTTP 返回 200 就把结果标记为"实时数据"。
结果在真实 API 配额耗尽、或返回了不符合预期的结构时，界面会把降级结果标成实时——这属于误导用户。

**修复**：每个 MCP 工具统一返回 `source` 与 `status`。
判定规则改为：**只有当 source 是真实来源名、且 status 为 ok 时，才视为实时数据**。
真实调用失败的结果既不冒充实时、也不冒充模拟，而是归入 `degraded` 或 `error`。
整体状态由各维度派生为 `live / degraded / mock / error` 四态，前端逐维度展示标签。

**沉淀**：数据可信度是产品语义，不能由"请求有没有报错"推断，更不能因为"看起来能跑"就默认它是真实的。

## 6. 助手回复的 Markdown 被当纯文本渲染

**现象**：助手回答里的 `**加粗**`、`- 列表` 原样显示成星号，界面观感很差。

**根因**：气泡直接用了 `<pre>` 输出原始文本，没有渲染层。

**修复**：接入 `react-markdown` + `remark-gfm` 渲染助手消息；
用户气泡仍保持纯文本，避免用户输入的 `*` 等符号被误解析。

**过程中发现的隐蔽坑**：换用 `react-markdown` 后，**单个换行默认被折叠成空格**，
而推荐语恰好是用单换行分行的（推荐语 / 天气提示 / 数据来源三行），
直接替换会让三行合并成一整段。因此补充 `remark-breaks`，让单个换行保持为换行。

**沉淀**：替换渲染层时必须验证"**原有格式没有退化**"，而不只是"新功能生效了"。
这次如果没有做前后截图比对，这个退化会直接带进线上。
