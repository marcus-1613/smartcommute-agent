# OpenTripPlanner（OTP）作为新加坡公交引擎的可行性评估

> 结论先行：**暂不引入 OTP，本轮不编写代码。** 本文档仅做技术评估，供后续在真实数据需求明确时决策。

## 1. OTP 是什么

OpenTripPlanner 是一个开源的多模式行程规划引擎，核心能力：

- 多模式路线规划：步行 + 公交 + 地铁 + 自行车的组合路由。
- 基于 GTFS（公交时刻表）+ OpenStreetMap（OSM，路网/步行）构建图。
- 支持出发/到达时间、可访问性、实时到站（GTFS-RT）扩展。
- 提供 REST API（Plan 端点），返回结构化行程（段、换乘、耗时、步行）。

## 2. 与我们需求的匹配度

| 维度 | 匹配情况 | 说明 |
|---|---|---|
| 公交/地铁路线规划 | ✅ 强匹配 | 正是 OTP 的核心能力 |
| 新加坡数据可用性 | ⚠️ 部分 | LTA 公开 GTFS 静态数据，可自行构建 |
| 实时到站/延误 | ⚠️ 需额外 | 需 GTFS-RT 实时源（LTA DataMall 提供部分） |
| 交通事件 | ❌ 不提供 | 需另接 LTA DataMall，与本轮 B 方案重复 |
| 天气 | ❌ 不提供 | 与 Open-Meteo（A 方案）正交 |
| 部署复杂度 | ❌ 高 | 需 Java + Docker + 图构建，运维成本高 |

**结论**：OTP 能解决"路线规划"这一个维度，但交通事件、天气仍需额外数据源。引入 OTP 不会减少当前依赖的组件数量。

## 3. 成本与门槛

### 3.1 许可
- OTP 采用 **LGPL-3.0** 许可。作为独立服务进程调用（REST 边界）通常可满足 LGPL 的分离要求，但需评估企业合规口径；若需静态链接或修改源码，则需开源衍生部分。对"仅 HTTP 调用"场景，许可风险可控，但需法务确认。

### 3.2 技术栈
- 运行依赖 **Java（JDK 17+）**，通常以 Docker 镜像部署。
- 需要本地构建 Graph 文件（GTFS + OSM），构建耗时且需定期更新（新加坡公交网络会调整）。

### 3.3 数据构建
- **GTFS 静态数据**：LTA 通过 DataMall 公开（需 AccountKey 下载）。
- **OSM 步行路网**：从 Geofabrik 下载新加坡 extract，或自行裁剪。
- 构建 Graph 需数 GB 内存与一定时间；更新频率建议每日/每周，形成运维管道。

### 3.4 部署
- 独立容器（`opentripplanner/opentripplanner` 官方镜像）。
- 相比当前"无 Key 即可跑的轻量 Mock"，OTP 属于重量级基础设施。

## 4. 与当前架构的接入方式（若未来引入）

- 保持适配器模式：新增 `OTPRouteService` 实现 `MobilityService` 接口。
- 通过 MCP Server（`mobility_server.py`）新增或替换 `get_routes` 的数据源，环境变量切换。
- 交通事件仍由 LTA 适配器提供，天气仍由 Open-Meteo 提供，与 OTP 解耦。

## 5. 建议

1. **当前阶段不引入 OTP**：Mock 已满足演示，LTA + Open-Meteo 已覆盖"真实交通事件 + 真实天气"。
2. **若需真实公交路线**：优先评估轻量方案（如直接调用 LTA 提供的路线/时刻表 API，或第三方公交 API），再考虑 OTP。
3. **OTP 适用场景**：需要完全本地化、无第三方依赖、可定制路由算法的生产级公交规划时再引入。
4. **若决定引入**：应作为独立服务部署，通过适配器接入，并补充图构建与更新的自动化管道。

## 6. 关键事实核对

- OTP 许可：LGPL-3.0（详见官方仓库 LICENSE）。
- LTA DataMall 提供 GTFS 静态数据下载（需 AccountKey），符合新加坡公交公开数据政策。
- 上述数据获取与部署细节需在实际接入时以官方文档为准，本文档不保证时效性。
